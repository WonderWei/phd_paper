# 可增长远端对象：快速验证实验设置

> 对应设计文档：`growable-remote-object-design.md`
> 目的：用最小代价判断 "Inline + Extent Directory" 是否值得做成完整原型，并在动手前明确 **go / no-go** 标准。

---

## 0. 要验证的假设

| 编号 | 假设 | 对应设计文档的论点 |
|---|---|---|
| H1 | 连续布局（2× size-class）在扩容边界产生明显的 **append 尾延迟** 与 **写放大**，而 extent 布局没有 | §5 Remote relocation amplification |
| H2 | extent 布局的读延迟 **接近** 连续布局，远好于细粒度链式布局 | §15–16 Extent directory + 并行读 |
| H3 | 在混合负载与真实对象大小分布下，extent 布局给出 **更好的整体 trade-off**（吞吐、尾延迟、内存利用率） | §22 better trade-off |

## 1. Phase 0：解析成本模型（已完成，约 1 小时）

脚本：`docs/growable-sim/sim.py`（纯 Python，无依赖）

```bash
python3 docs/growable-sim/sim.py                 # 远端分配需 1 RTT
python3 docs/growable-sim/sim.py --alloc-rtt 0   # CN 本地预领块，分配 0 RTT
```

模型参数：RTT = 2 µs，100 Gbps，header 64 B，inline 256 B，header 内最多 24 个 extent 指针，超出后走一级间接块。Append 统一按 "CAS 加锁 → 写数据 + size + 解锁" 2 RTT 计。

对比布局：`Contig-2x`（2 倍 size-class，溢出即搬迁）、`Linked-256/1024`（带 tail 指针的链式块）、`Ext-1024`（本设计）、`Geo-1024`（extent 大小倍增）、`Ext-1024+cache`（CN 缓存 extent 目录）。

### 1.2 Phase 0 结论（会改变实验重点）

1. **单次搬迁代价很大，但在单线程、无竞争时会被摊薄。** 每次搬迁的停顿时间约为 `alloc + RTT + 2·size/BW + publish`：4 KB 约 7 µs，64 KB 约 17 µs，1 MB 约 0.17 ms，16 MB 约 2.7 ms。倍增扩容使搬迁只发生 log₂ 次（64 B append 增长到 64 KB 时，约 1020 次 append 中只有 8 次搬迁），所以在单线程、无竞争的模型里，Contig 的 append 均值与 Ext 持平（4.06 vs 4.13 µs）。设计文档 §5 的 "放大 128 倍" 是单次峰值；摊销写放大约 **3×**（CN 必须先 READ 旧数据再 WRITE，比文档估计多一倍）。
   **模型没有计入的代价：** 搬迁期间对象锁一直被持有，其他 writer 必须排队，热点对象会把这段停顿放大成排队延迟；搬迁时间与对象大小成正比，MB 级对象会出现毫秒级停顿；多个对象同时搬迁会占用网卡带宽；旧副本还需要 grace period 才能回收。reader 可以继续读旧副本（写已被锁住，旧副本内容仍然一致），只是在 publish 之后需要发现地址变化并重试。
   → 真正能赢的指标是 **尾延迟**、**热点对象上的并发排队** 和 **带宽受限时的吞吐**，不是单线程平均延迟。实验以 E1（多线程）、E4（并发读写）为主，并把 E1 的对象上限扩展到 1–16 MB。
2. **中等对象的读要多一个 RTT。** 512 B – 4 KB 对象的读延迟约为 Contig 的 **2 倍**（先读 header、再读 extent）。§16 的 "两阶段" 正是这个代价，而这个区间恰好是最常见的增长区间。
   → 必须加一种 1-RTT 读路径：**缓存目录**（extent 永不搬迁，缓存的目录只会变长、不会失效）或 **把首个 extent 地址放进索引项**。这一点是区别于 Contig 的真正卖点，应升级为设计原则。
3. **固定 1 KB extent 会撑爆 header 目录。** 64 KB 需要 64 个 extent，超过 header 容量后要走间接块，多一次 RTT（14.5 vs 7.25 µs）。倍增 extent 能解决这个问题，但内存利用率会掉到 55%。
   → 原型应采用 **"前几个固定 + 之后倍增，并设上限"** 的混合策略，并单独做消融。
4. 内存利用率比 Contig 只高约 5 个百分点：可以作为附带收益，不宜当主卖点。

### 1.3 W4：新分配的地址如何让其他 CN 知道

W1–W3 只算了 appender 自己的分配与发布开销，并假设读者总持有正确地址。W4 补上读者一侧：一个对象用 64 B append 持续增长，8 个 CN 同时读它（每次 append 对应 4 次读），每个 CN 缓存上次读到的元数据。

| 布局 | 读者如何发现变化 | 过时时的额外代价 |
|---|---|---|
| Contig-2x | 缓存 (地址, 代号)；搬迁时在旧 header 写 tombstone | 读旧副本 → 遇到 tombstone → 重读索引 → 读新副本，+2 RTT |
| Ext-1024 | 不缓存，每次先读 header | 0，但每次读固定 2 RTT |
| Ext/Geo+cache | 缓存目录，一轮推测读 header + 已知 extent | header 显示有新 extent 时，再读一轮，+1 RTT |

结果（alloc = 1 RTT，延迟单位 µs）：

| 对象 | 布局 | 读 mean | 读 p99 | 读到过时元数据 | append p99.9 | append max |
|---|---|---|---|---|---|---|
| 64 KB | Contig-2x | 4.69 | 7.22 | 1.5% | 12.63 | 15.25 |
| 64 KB | Ext-1024+cache | 6.52 | 11.89 | **12.5%** | 6.01 | 6.01 |
| 64 KB | Geo-1024+cache | 4.95 | 7.58 | 1.4% | 6.01 | 6.01 |
| 1 MB | Contig-2x | 43.96 | 85.06 | 0.1% | 4.01 | **93.89** |
| 1 MB | Ext-1024 | 73.53 | 139.8 | 0 | 6.01 | 6.01 |
| 1 MB | Geo-1024+cache | 44.44 | 85.58 | 0.1% | 4.01 | 6.01 |

结论：

1. **Contig 的地址发现代价本身不大。** 搬迁只发生 log₂ 次，每个 CN 在每次搬迁后只多付一次 +2 RTT，过时读占 0.1%–1.5%。它真正的难点在正确性：旧副本必须保留 tombstone，直到所有可能缓存旧地址的 CN 都刷新过，否则会读到被回收后重用的内存。这需要 lease 或跨 CN 的 epoch 机制，属于回收复杂度，而不是延迟问题。
2. **"extent 地址永不变化" 不等于 "没有发现代价"。** 读者仍要发现新增的 extent。固定 1 KB extent 的新增频率是倍增搬迁的约 8 倍，导致 12.5% 的读过时。倍增 extent 的发现频率降到和 Contig 一样（1.4%），并且每次只需 +1 RTT，不需要回索引。
3. **分配频率对 append 的影响。** Contig 每次倍增分配一次，固定 extent 每 1 KB 分配一次。分配做成远程 RPC（2 RTT）时，Ext-1024 的 append 均值变为 4.26 µs，略差于 Contig 的 4.08 µs。倍增 extent 的分配次数与 Contig 相同。
4. **固定 1 KB extent 不适合 MB 级对象。** 1 MB 需要约 1000 个 extent 和 1000 个 READ verb，读延迟比 Contig 高 67%。倍增 extent 与 Contig 基本持平（44.4 vs 44.0 µs），同时把 append 最大值从 94 µs 降到 6 µs。

→ 原型应以 **倍增（或混合）extent + 目录缓存** 作为主方案，固定 1 KB extent 只作消融。Phase 1 的 E4 需要额外测：tombstone 命中率、跨 CN 回收等待时长、过时目录导致的额外轮次。

> 模型 **未覆盖**：NIC 消息速率上限（多个小 READ vs 一个大 READ）、多线程带宽饱和、读者在搬迁期间的重试、旧副本回收。这些只能在 Phase 1 用真机测量，而它们正是 H1/H2 能否成立的关键。

## 2. Phase 1：RDMA 微基准（约 1–1.5 周）

### 2.1 环境

- **硬件：** 2–3 台机器，ConnectX-5/6（100 Gbps）。1 台作 MN，1–2 台作 CN。没有本地集群可用 CloudLab（如 `r6525`/`c6525-100g`）。SoftRoCE 只能用来调正确性，**不能**用来测性能。
- **实现：** C++ + libibverbs，全部使用 one-sided verbs。MN 只负责注册一块大 MR（如 32 GB，开 hugepage），之后不再参与任何操作。
- **分配器（刻意简化）：** MN 内存按 CN 预先切区，CN 在本地 bump/free-list 分配，**分配 0 RTT**，对所有布局一致，避免分配器成为变量。
- **并发控制：** 统一使用 header 中的 lock + version（seqlock），所有布局相同。
- **回收：** Contig 的旧副本延迟 free（固定 grace period），记录被延迟的字节数。

### 2.2 被测布局

| 名称 | 说明 | 作用 |
|---|---|---|
| `Contig-2x` | 2 倍 size-class，溢出即搬迁 | 主 baseline（读最优） |
| `Linked-256` | 256 B 链式块 + tail 指针 | 主 baseline（增长最优） |
| `Linked-1K` | 1 KB 链式块 | 消融：只有 "粗粒度"，没有目录 |
| `Ext` | inline 256 B + 1 KB extent + header 目录 | 本设计 |
| `Ext-hybrid` | 前 8 个 1 KB，之后倍增，上限 16 KB | 修复目录溢出 |
| `Ext+cache` | `Ext-hybrid` + CN 侧目录缓存，1 RTT 推测读 | 修复中等对象多出的 RTT |
| `Ext-noinline` | 去掉 inline 区 | 消融：inline 的价值 |

### 2.3 实验列表

| 编号 | 负载 | 变量 | 指标 | 验证 |
|---|---|---|---|---|
| **E1** 增长 | 每线程独占对象，从 0 增长到 64 KB / 1 MB / 16 MB | append 大小 {64 B, 256 B, 1 KB, 4 KB}；线程 {1, 8, 32} | append p50/p99/p99.9，吞吐 (Mops)，**网卡实际字节/逻辑字节** | H1 |
| **E2** 静态读 | 预先构建对象，只读 | 对象大小 {128 B … 256 KB}；线程 {1, 32} | 读 p50/p99，吞吐 (Mops 与 Gbps) | H2 |
| **E3** NIC 压力 | 32 线程读 64 KB 对象 | extent 大小 {512 B, 1 KB, 4 KB, 16 KB} | 吞吐 vs 单个 64 KB READ | H2：多个小 READ 是否撞上消息速率上限 |
| **E4** 并发读写 | 多个 appender + K 个 reader 访问同一热点对象（64 KB–16 MB） | appender {1, 4}；K {1, 4, 16} | append 排队延迟 p99，reader 重试率，reader p99，回收延迟字节 | §6 地址稳定性 |
| **E5** 混合 | 100 万 key，Zipf 0.99，大小分布同 W3 | 读:append = 95:5 / 50:50 / 5:95 | 总吞吐，读/写 p99，内存利用率 | H3 |
| **E6** 消融 | 同 E5 的 50:50 | 逐项关闭 inline / 目录 / 缓存 / 倍增 | 同 E5 | 各设计点的贡献 |

每组运行至少 30 s，预热 5 s，重复 3 次，报告中位数。延迟用 CN 本地 `rdtsc` 记录，用 HdrHistogram 统计。

### 2.4 Go / No-Go 标准

| 标准 | 通过条件 | 不通过时的处理 |
|---|---|---|
| G1 增长 | E1 中 append ≥ 1 KB、32 线程时，`Ext` 吞吐 ≥ 1.3× `Contig`，**或** p99.9 ≤ ½ `Contig` | 放弃 "搬迁放大" 叙事，改以尾延迟、地址稳定性（E4）为主 |
| G2 读 | `Ext+cache` 读 p50：0.5–4 KB 对象 ≤ 1.3× `Contig`，64 KB 对象 ≤ 1.5× | 加入 "索引项内嵌首个 extent" 或调大 inline |
| G3 NIC | E3 中 1 KB extent 吞吐 ≥ 单个大 READ 的 70% | 增大 extent 粒度，或使用倍增 extent |
| G4 整体 | E5 至少一种混合比例下比 `Contig`、`Linked` 都好 ≥ 10%，其余比例不差于 10% | 说明 trade-off 不成立，需要重新审视问题 |

G1 与 G4 都不通过时，建议停止推进这个方向。

## 3. 吞吐模拟（`growable-sim/tput_sim.py`）与预期结果形状

模型：32 个闭环线程，1 CN + 1 MN，网卡 40 Mverbs/s、双向各 100 Gbps，RTT 2 µs，两种方案均为本地分配。下表中的提升都相对于 Contig-2x。

| 层次 | 负载 | 吞吐提升 | append p99.9（Contig → Ext） |
|---|---|---|---|
| 吞吐明显提升 | 只追加，1 KB / 4 KB append | +42% / +66% | 410 → 4.7 µs / 1011 → 12.7 µs |
| 吞吐明显提升 | 50% 读尾部 + 1 KB append | +34% | 18.8 → 4.4 µs（全部操作） |
| 吞吐明显提升 | 只追加，对象增长到 16 MB | +62% | 673 → 4.7 µs |
| 吞吐小幅提升 | 只追加，256 B append | +20% | 85 → 4.1 µs |
| 吞吐小幅提升 | 90% 读尾部（精简读路径） | +8% / +14% | 12.6 → 4.2 µs（全部操作） |
| 吞吐基本持平 | 64 B append | +5% | 42 → 4.1 µs |
| 吞吐基本持平 | 4–32 个线程追加同一个热点 key | +3% ~ +7% | 192 → 10 µs（4 线程） |
| 两项都持平 | 50% 读整个 64 KB 对象（入方向带宽打满） | +3% | 读延迟主导，p99 约 100 µs，两者相近 |

**设计修正：** 读尾部时，若目录已缓存，只读 8 B 版本字加尾部 extent，不读完整 header。不做这一修正时，90% 读的负载吞吐会下降 5–10%；修正后变为提升 8–14%。
